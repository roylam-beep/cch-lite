重講 $ARGUMENTS。留空就重講上一輪你自己的輸出；給檔案路徑就讀那個檔；給文字就重講那段。

## 先判是哪一種

- **指著一塊問**——使用者引用了一段、用 `<--` 指著某個詞、或問「X 是什麼意思」＝**只講那一塊**，三行內：
  它是什麼／你為什麼會碰到它／你要不要做什麼。不重講整份。
- **其餘**（留空、整份計畫、報告、錯誤訊息）＝照〈寫法〉重講整份。
- **同一件事第二次被叫**＝上一版的講法失敗了。不准用同一種寫法再來一遍：換成日常比喻或圖，句子再砍一半。

## 硬規則

1. **不辯解，不道歉**。使用者說看不懂，就是你上一版寫壞了，直接重講。道歉不超過半句，通常是零句。
2. **不新增資訊、不新提案、不改檔案**。這是同一件事的另一種說法，不是下一步工作。範圍外的想法一律不寫。
3. **不確定就說不確定**。不要用聽起來完整的句子把不確定蓋過去。

## 寫法

### 開頭一句背景
先講「你為什麼會碰到這件事」，把讀者定位好。例：

> 背景：你被那個權限彈窗煩到，問能不能一次允許。下面是同一份計畫，換白話講。

### 三段，條列，一點一句
每段一個粗體小標題，標題本身就是白話動作句或問句，不要用名詞術語當標題。

- 計畫／建議：**我會做什麼**／**做完會變怎樣**／**你要做什麼**
- 報告／現況：**現在的情況**／**問題在哪**／**你要做什麼**
- 真的有風險才加第四段 **最怕的事**（最壞情況＋怎麼擋住）；沒有就不寫。
- 壞標題：**架構變更**／**實作細節**／**風險評估**

主動語態，句子短。一個逗號串三個概念就是要拆。

### 術語當場付現
第一次出現的名詞，後面立刻用一句白話說它是什麼、為什麼這裡會碰到它。做不到就不要用那個名詞，改用白話把事情講完。
**編號、代號、縮寫也算**：不准拿 `#17`、`L3`、`R13` 當主詞，寫出它指的是哪件事。

- 好：「延遲載入工具（工具的說明不是一開始就在，我每要用一個新工具得先跑一次搜尋）」
- 壞：「因為 deferred tool loading 導致 context 膨脹」

### 一律不翻的東西
**檔案路徑、指令、函式名、API 欄位名、設定值、數字，原樣精確寫出。**
這些是使用者要直接拿去用的，翻成白話近似說法就廢了。

- 對：「改 `src/server.ts` 裡兩個地方」
- 錯：「改一下伺服器的主程式」

### 把「這件事有多大」講成使用者感覺得到的東西
用「要改幾個檔」「資料已經有了不用自己想」「最怕標錯會怎樣」這種說法，
不要用抽象形容詞（複雜／中等難度／有一定風險）。

### 有分支或多方關係就畫圖
要重講的東西是有分支的流程、三個以上東西互相連、或改前改後對照＝畫一張 inline widget
（`mcp__visualize__show_widget`，第一次呼叫前先跑 `mcp__visualize__read_me`，不用跟使用者報告），
文字壓到 5 行內。份量上限照 `/cc-show`。圖只畫原本講過的東西。沒有 visualize 工具就照文字寫。

### 結尾補前提條件
如果做完還不會生效、還要別人配合、還缺權限或憑證——在最後講明。
不知道使用者有沒有那個權限，就直接說不知道。

## 長度

預設 15 行內。使用者明說「完整」「詳細」「報告」才放長。
真的講不完就寫檔，回覆只給路徑加三行摘要。

## 結尾禁止

不反問、不提新方案、不問「這樣清楚嗎」。講完就停。

## 參考範本

一份合格輸出長這樣（結構，不是內容）：

```
背景：<一句話，你為什麼會收到這個>

**我會做什麼**
- <一點一句；改哪個檔、改幾處，路徑原樣寫>

**做完會變怎樣**
- <使用者看得到的那面>

**你要做什麼**
- <要按什麼、要等什麼、缺的權限、不知道的部分>
```

## 防什麼

技術輸出使用者看不懂，還得自己追問第二次才拿到能懂的版本；或只指著一個詞問，卻被整份重講。
